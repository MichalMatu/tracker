# Local Agent Autopilot

This file extends `LOCAL_AGENT_FLOW.md` with the autonomous iteration contract for `MichalMatu/tracker`.

## Trigger

When the user says an equivalent of `uzyj local-agent autopilot`, `zrob autonomicznie przez local agenta`, `napraw do skutku przez local agenta`, or `autopilot until green`, read both this file and `LOCAL_AGENT_FLOW.md`.

## Core loop

Do not stop merely because a task was queued or because a Gradle build/test is still running.

Within the active ChatGPT turn:

1. confirm the exact tracker repository/binding identity;
2. inspect source and prepare the smallest deterministic patch;
3. set `resources: []`;
4. queue the task with the exact tracker `agent_binding`;
5. follow `.agent/results/<task-id>.json` on `agent-control`;
6. inspect exit codes, output, `git_status` and `git_diff`;
7. diagnose failures from real evidence;
8. queue a new uniquely-id'd corrective task when needed;
9. rerun the smallest affected gate first;
10. broaden verification progressively only after focused checks pass;
11. publish only validated source.

The user should not need to paste daemon logs or say `sprawdz` between iterations.

## Resource rules

- every Local Agent task in this repository uses `resources: []`, including Kotlin/Compose/Gradle work and ADB/install/logcat or physical-phone validation;
- detect and verify the intended device inside the task; do not declare named resources or `machine` from this repository.

`memory_limit_mb` is an independent watchdog and does not change the repository-wide `resources: []` policy.

## Verification strategy

Use the narrowest failing gate first. Examples:

- Kotlin compile error -> rerun only the affected module compile/test;
- Detekt failure -> fix the reported issue and rerun that module's Detekt;
- ktlint failure -> rerun that module's ktlint check;
- unit test failure -> rerun the affected test/module;
- app integration/build issue -> `:app:assembleDebug` after focused checks;
- broad completion gate -> `qualityCheck` only after focused verification is green.

Do not silence a real quality failure by expanding baselines or adding suppressions unless the repository policy and evidence justify it.

If an active task is healthy, do not queue a duplicate or poll it every 30 seconds. With Chat Bridge, use no sooner than about two minutes for an early liveness re-check and normally 5-10 minute `NEXT` pacing for multi-minute Gradle/build/test work unless exact evidence supports a nearer completion. Explicit `NEXT=30s` remains available for deliberate operator/emergency use.

If exact current run/status evidence already proves that an active task cannot achieve its intended outcome, publish one repository-scoped `cancel_task` request for that exact task id, wait for cancellation/terminal result evidence, and only then queue replacement work. Do not wait for a long timeout once failure is already unavoidable, and do not cancel solely because a healthy task is slower than expected.

## Java 21 runtime / JVM 17 target

The repository uses **JDK 21** as its installed Gradle/compiler runtime while generated bytecode remains **JVM 17**. Do not require a separate JDK 17 installation. On the established Mac environment resolve JDK 21 with:

```bash
export JAVA_HOME="$(/usr/libexec/java_home -v 21)"
```

Routine software-only builds/tests should prefer the ChatGPT sandbox or exact-SHA GitHub Actions evidence. Local Agent/Mac remains the hardware/runtime worker unless Mac-specific reproduction is required.

## Physical-phone work

When the user has already authorized physical-phone validation and the device is connected, continue through safe ADB stages after software checks pass:

1. build the debug APK;
2. discover/confirm the intended device with `adb devices`;
3. install/update the debug build using the repository-approved command;
4. capture bounded logcat/runtime evidence relevant to the change;
5. analyze evidence and iterate if required.

Stop for user action only when the phone must be unlocked, permission must be granted manually, a cable/device must be reconnected, or another genuinely physical/manual step is required.

## Stop conditions

Pause autonomous work only when:

- a physical/manual action is required;
- an ambiguous product decision cannot be resolved from repository context;
- credentials/secrets/permissions unavailable to the agent are required;
- the next operation is materially destructive or outside the authorized scope;
- repeated evidence shows an infrastructure failure that cannot be corrected from repository work;
- work must move to another repository and the conversation is not explicitly rebound;
- the user asks to pause.

Compiler errors, test failures, lint failures, Detekt findings, deterministic patch mismatches and ordinary Gradle failures are not reasons to stop; diagnose and iterate.

## Branch discipline

Normal autonomous work targets `main` as defined by `AGENTS.md` and `LOCAL_AGENT_FLOW.md`. Do not silently switch to historical branches such as `field-mvp-work` or portfolio branches. If a goal explicitly concerns merging/recovering an old branch, treat branch comparison and merge validation as part of the requested work.

## Chat Bridge continuation

If Chat Bridge is enabled, every wake must remain exactly bound to tracker:

```text
LA_AGENT=be481b25-9d97-4205-b93f-95f5c5827441
LA_REPO=tracker
LA_REPOSITORY=MichalMatu/tracker
```

While work remains unfinished or is waiting for executor capacity/resources, continue with `[LAB:NEXT=<duration>]`. Use `[LAB:STOP]` only when the requested goal is fully evidenced and `[LAB:PAUSE]` when a real user/manual action or explicit Rebind is required.

For a healthy active task, autonomous `NEXT` pacing must not use 30-second polling. Use an early re-check no sooner than about two minutes and normally 5-10 minutes for multi-minute work. If exact evidence proves the active task is doomed, cancel that exact task id and wait for the terminal cancellation/result before replacing it.

## Completion

Do not report success until the requested focused checks and appropriate broad gate are actually green, the final diff is reviewed, and validated source is published according to repository policy. Physical-phone runtime evidence is a separate completion gate when the task explicitly requires it.
